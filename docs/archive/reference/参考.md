  Claude Code 源码分析 vs EmoAgent：可借鉴的点

  1. 主循环状态机设计 — Phase 4-5 直接可用

  Claude Code 的 query.ts 是一个 while(true) + state 对象的状态机，每次迭代走完：压缩上下文 → 组装 prompt → 调 API →
  处理工具 → 继续/退出。

  EmoAgent 现状：chat/engine.go 是一个简单的"收消息 → 调 LLM → 返回"的单轮模式，没有工具循环。

  建议：Phase 4（Tool System）实现时，Engine 需要改造成类似的 agent loop：
  用户输入 → 组装 prompt → 调 LLM → 有 tool_call?
    → 是：执行工具 → 结果拼回 messages → 再调 LLM（循环）
    → 否：返回文本给用户
  这就是你架构文档里 Work agent 的"多轮自循环"，但 Emotion agent 做简单工具调用也需要这个循环。

  ---
  2. 工具执行 Pipeline — Phase 4 核心参考

  Claude Code 的工具执行不是"模型说调就调"，而是一条 14 步流水线：校验输入 → 权限检查 → hooks → 执行 → 后处理。

  对 EmoAgent 的启示：

  - 输入校验：用 JSON Schema 校验工具参数（你的设计已有）
  - 权限分级：EmoAgent 的 TaskBrief.PermissionScope 已经定义了权限边界，工具执行时要校验
  - fail-closed 默认值：新工具默认不安全、不可并发、需要权限检查。这个理念直接适用于 Work agent 的工具注册

  ---
  3. 角色分离 — 你已经领先了

  Claude Code 有 6 个内建 Agent（Explore、Verification、Plan 等），核心思路是"做事的人和验收的人分开"。

  EmoAgent 的双核架构天然就是这个模式：Emotion 拥有对话和决策，Work 执行任务。而且你的设计比 Claude Code 更严格 — Work
  完全不可见于用户，上下文严格隔离。

  可以额外借鉴的：Claude Code 的 Verification Agent 思路。Work 执行完任务后，可以考虑让 Emotion 用一个"验证视角"的
  prompt 来审查 TaskReport，而不是无条件信任。

  ---
  4. 上下文压缩 — Phase 5 核心参考

  Claude Code 的四道压缩机制值得直接借鉴：

  ┌──────────────────┬─────────────────────────────┬──────────────────────────────────────────┐
  │       机制       │         Claude Code         │              EmoAgent 适配               │
  ├──────────────────┼─────────────────────────────┼──────────────────────────────────────────┤
  │ Snip Compact     │ 裁剪历史消息过长部分        │ 裁剪单条消息中过长的工具结果             │
  ├──────────────────┼─────────────────────────────┼──────────────────────────────────────────┤
  │ Micro Compact    │ 按 tool_use_id 缓存编辑     │ Work 执行中间结果的增量压缩              │
  ├──────────────────┼─────────────────────────────┼──────────────────────────────────────────┤
  │ Context Collapse │ 不活跃区域折叠成摘要        │ 老对话折叠成摘要（你的 KeepRecent 策略） │
  ├──────────────────┼─────────────────────────────┼──────────────────────────────────────────┤
  │ Auto Compact     │ 总 token 接近阈值时全量压缩 │ ~40k token 触发压缩（你的设计已有）      │
  ├──────────────────┼─────────────────────────────┼──────────────────────────────────────────┤
  │ Reactive Compact │ API 413 兜底                │ 必须有，作为最后防线                     │
  └──────────────────┴─────────────────────────────┴──────────────────────────────────────────┘

  关键点：你的设计文档里写了"~40k token 触发压缩，保留最后 6 轮"，这对应 Claude Code 的 Auto Compact。但建议加上 Snip 和
   Reactive 作为前置和兜底。

  ---
  5. Prompt 组装与缓存 — 现在就可以优化

  Claude Code 把 system prompt 分成静态部分（可缓存）+ 动态部分（按会话变化），中间用 boundary 分隔，利用 API
  的前缀缓存降低成本。

  对 EmoAgent 的启示：
  - Persona 的 system_prompt 是相对稳定的 → 放在前面
  - 会话上下文摘要、当前情绪状态 → 放在后面
  - 如果使用 Anthropic API，这种排列能直接利用 prompt caching，省钱

  ---
  6. 行为规范写成制度 — Emotion prompt 设计参考

  Claude Code 最有价值的设计之一：原则1 —
  不信任模型的自觉性。所有行为规范（不要乱加功能、先读再改、不要过度抽象）都写进了 system prompt。

  对 EmoAgent Emotion agent 的启示：
  - "永远不暴露 Work 的存在" → 写进 system prompt
  - "不主动提起记忆中的敏感内容，除非用户先提" → 写进 system prompt
  - "委派判断标准：1-2步的自己做，多步的派 Work" → 写进 system prompt
  - 不要依赖模型"领悟"这些规则，要制度化

  ---
  7. 产品化思维 — 长期参考

  文章总结的原则7：产品化在于处理第二天 — 任务中断怎么续？脏状态怎么清？进程泄漏怎么办？

  EmoAgent 当前阶段还不需要太担心这些，但在 Phase 6（Work Runtime）时要考虑：
  - Work 执行中断（LLM 超时、网络断开）→ TaskReport 标记 failed，记录到哪一步了
  - 多个 Work 并发时的资源清理
  - Session 恢复后 Work 状态的一致性

  ---
  当前阶段的优先级建议

  EmoAgent 完成了 Phase 0-3（基础设施 + 聊天 + WebUI + 配置管理），接下来是 Phase
  4（工具系统）。从这篇分析中，最值得立刻落地的三件事：

  1. 把 Engine 改造成 agent loop（while 循环 + tool_call 检测 + 工具执行 + 结果回注）
  2. 工具接口设计参考 Claude Code 的 Tool 基类：inputSchema、权限检查、只读标记、并发安全标记，用 fail-closed 默认值
  3. Emotion 的 system prompt 制度化：把所有行为规范（不暴露 Work、委派判断标准、记忆使用规则）明确写进
  prompt，不依赖模型自觉
