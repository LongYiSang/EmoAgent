# 开发者工作台

**这里是现行的、可执行的。** 判断当前行为，以这里和代码为准。

`docs/architecture/` 是设计意图（细节可能滞后），`docs/archive/` 是历史快照（不代表现在）。三者的区别见 [`docs/README.md`](../README.md)。

## 内容

**[`invariants.md`](invariants.md)** —— 跨模块硬约束。动代码前先扫一眼，看你要碰的地方有没有被约束住。

**`recipes/`** —— 变更配方。一类常见改动一份，回答"碰哪些文件 / 必须同步改什么 / 怎么验证"：

| 配方 | 覆盖 |
|---|---|
| [`recipes/add-plugin.md`](recipes/add-plugin.md) | 写插件。**加功能的主路径**，含五个不报错的失败模式 |
| [`recipes/add-builtin-tool.md`](recipes/add-builtin-tool.md) | 加内置工具，含两个编译不会拦住你的漏改点 |
| [`recipes/add-migration.md`](recipes/add-migration.md) | 改 `data/emo.db` 结构 |
| [`recipes/change-frontend.md`](recipes/change-frontend.md) | 改 `web/`，含 `go:embed` 吐旧产物的陷阱 |

配方是按需增补的，不求覆盖全部改动类型 —— 低频配方写完可能很久用不上一次，也就无从验证对错。碰到一类反复出现、每次都要重新摸索的改动，就照下面的规则补一篇。

## 只写代码里读不出来的东西

这条规则是这个目录能不能活过三个月的关键，请后来者一起守。

**该写：**

- 耦合关系 —— 改了 A 必须同步改 B，而编译器不会提醒你
- 约束的理由 —— 为什么不能这么做，违反了会发生什么
- 验证方式 —— 改完怎么证明它真的生效了

**禁止写：**

- 包列表、数据表列表、API 端点列表
- 架构再描述、目录结构说明

后面这些仓库根的 `CLAUDE.md` 索引已经够用，而且它们腐烂得最快 —— 写进来，三个月后这里就变成又一份不可信的文档，正是本目录存在的意义所要消灭的东西。

判断标准很简单：**这句话能不能靠 grep 代码得到？** 能，就别写。

## 写新配方的规则

统一四段结构：

| 段 | 内容 |
|---|---|
| **何时用** | 一句话说明这个配方覆盖哪类改动 |
| **锚点文件** | 表格形式：文件 / 必须做什么 / 漏了会怎样 |
| **步骤** | 按顺序，**明确标出哪些是"必须同步改"** |
| **验证命令** | 可直接运行的命令，跑通即证明改对了 |

**验证命令段不是可选的。** 它是这份文档的防腐机制：配方过期时，使用者跑一遍命令就当场发现，而不是被静默误导。

### 锚点选择规则

`internal/devdocs` 里的测试会扫描本目录下所有 Markdown，把反引号包裹的仓库路径逐一断言存在。文件被重命名时测试变红，并直接指出是哪篇文档失锚。所以：

- 只用**仓库内被 git 追踪的稳定路径**做锚点
- **不用**版本化或运行时生成的路径 —— 插件安装快照 `data/plugins/packages/<id>/<version>/`、`data/*.db`、构建产物等。它们升级即失效、卸载即消失，且不在版本控制里，干净克隆上根本不存在
- 需要指向一个完整的真实例子时，用**源码仓库 URL**，不要指向本机的安装结果
- 行号只写在正文里辅助定位，**不作为校验目标** —— 行号会随代码漂移，校验它只会制造假警报

改完文档跑一次：

```bash
go test ./internal/devdocs/ -v
```
